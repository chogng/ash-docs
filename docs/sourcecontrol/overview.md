# 使用 Git 管理代码更改

Ash 的 Git 侧栏可以查看文件更改、选择下一次提交的内容，以及浏览提交历史。本指南带你完成一次从检查更改到提交、推送的工作流程，也介绍分支切换和常见错误的处理方式。

本文依据当前主分支源码介绍桌面工作台中的 Git 操作；公开安装包的功能以实际版本为准。先在一个可以安全试验的仓库中练习，并保存编辑器里的文件。

## 打开或创建仓库

Ash 使用系统 Git，最低要求 **Git 2.40.0**。开始前，在运行 Ash 的环境中执行 `git --version` 检查版本，并为仓库配置提交者姓名和邮箱。远端操作还需要对应仓库的访问权限和可用认证。

Git 版本过旧时，Ash 会显示升级提示并停止仓库发现。升级后重启 Ash；如果设置了 `git.path`，也要把它改为升级后的 Git 路径。Desktop、App Server、TUI 和 Agent 使用同一最低版本要求。

1. 打开已有 Git 仓库所在的文件夹。
2. 在活动栏选择 **Git**，展开 **更改**。
3. 如果打开了多个仓库，在 **仓库** 视图中选择要处理的仓库，再核对底部状态栏的分支名称。

没有本地仓库时，可以选择以下入口：

* 克隆已有仓库：在命令面板运行 **Git: 克隆仓库**，输入仓库地址，选择保存它的父文件夹。克隆完成后，选择 **打开仓库**。
* 开始一个本地项目：打开项目文件夹，在命令面板运行 **Git: 初始化仓库**，按提示选择工作区文件夹并输入初始分支名称。Ash 不会在已有仓库内部创建嵌套仓库。

克隆入口用于桌面应用。克隆失败时，先检查地址、保存位置和 Git 访问权限。

## 检查文件更改

**更改** 视图按提交状态组织文件：

* **Changes**：工作文件相对于暂存区的更改。
* **Staged Changes**：已放入暂存区、准备进入下一次提交的更改。
* **Merge Changes**：需要处理的合并冲突。

从 **Changes** 打开的比较标签带 **工作树**（**Working Tree**），从 **Staged Changes** 打开的标签带 **索引**（**Index**），用来与普通文件标签区分。比较视图中的差异标记属于当前比较；普通编辑器侧边的 Git 更改标记不叠加到比较视图。

这些分组只在有对应文件时显示。同一个文件可以同时出现在前两个分组中，例如你暂存文件后又继续编辑了它。

1. 选择 **Changes** 中的文件，查看暂存区与工作文件的比较。
2. 选择 **Staged Changes** 中的文件，查看最近一次提交与暂存区的比较。
3. 对照修改目标检查新增、删除和替换的内容，确认没有混入其他任务的更改。

从 **Changes** 打开的单文件文本比较中，未删除文件的工作副本一侧可以继续编辑，也会保留该文件已有的未保存修改。原始一侧、**Staged Changes** 和历史快照仍然只读。多文件集中比较不属于这一可编辑范围；需要修改时，打开对应工作文件。二进制文件不能作为普通文本差异编辑。

在可编辑的并排比较中，可以使用更改块旁的 **还原更改**，或选中修改范围后使用 **还原选中的更改**。这两种操作只修改工作副本编辑器，不弹出保存确认，也不会立即写入磁盘。需要恢复时，在修改后的一侧使用撤销；确认结果后保存文件，才把还原后的内容写入磁盘。暂存区不受影响。这与 Git 侧栏中需要确认的文件放弃操作不同。

文件较多时，打开视图标题栏的 **更多操作 > 视图和排序**，切换树形或列表，并按路径、名称或状态排序。也可以使用分组的 **View All Changes** 或 **View All Staged Changes** 操作集中检查多个文件。

### 区分 Git 更改和聊天中的更改

Git 侧栏检查当前仓库的工作文件、暂存区和提交。聊天输入框上方的更改入口按当前页面使用另一种范围：

* **New Chat**：汇总工作区中多个仓库的 Git 更改。
* 已创建的对话：比较当前 Thread 的初始目录快照与当前有效检查点，只显示该对话的净变更。

因此，对话统计可能与 Git 侧栏不同。提交文件不会清空对话的历史变更，撤销或重做则让统计跟随恢复的检查点。没有对话净变更时，入口隐藏，不显示工作区统计作为替代。

**Conversation Changes** 是固定检查点的只读审阅，后续工作文件变化不会改写已打开的比较。提示对话已变化或 **Changes unavailable** 时，重新打开更改入口重试。工作区增删行数旁的 `*` 表示不包含无法按文本比较的文件，这些文件仍计入文件数。

先确认自己是在检查工作区状态，还是复查对话结果，再选择暂存和提交操作。更多说明见[检查当前对话的文件更改](/docs/agents/sessions.md#检查当前对话的文件更改)。

已关联 GitHub PR 的 Agent 会话还可以查看检查注释、下载作业日志、重新运行作业，或发送修复请求。操作和重试前的注意事项见[查看和处理 CI 检查](/docs/agents/sessions.md#查看和处理-ci-检查)。

## 选择要提交的内容

暂存决定下一次提交包含什么，不会创建提交。

1. 在 **Changes** 中检查一个文件。
2. 选择该文件旁的加号暂存文件。
3. 在 **Staged Changes** 中重新打开它，确认提交范围。

要取消暂存，选择已暂存文件旁的减号。文件的实际修改仍然保留。要批量处理，可以使用分组操作，或命令面板中的 **Git: 暂存所有更改**、**Git: 取消暂存所有更改**。

### 只暂存一部分修改

当一个文件包含多个独立修改时，可以按更改块或选中行暂存：

1. 按更改块操作：运行 **Git: 暂存更改块**，选择文件，再检查并选择一个更改块。
2. 按行操作：从 **Changes** 打开当前比较，选中要暂存的修改行，再运行 **Git: 暂存选中行**。
3. 返回 **Staged Changes** 检查结果。需要调整时，从当前已暂存比较选择行，运行 **Git: 取消暂存选中行**，或使用 **Git: 取消暂存更改块**。

也可以在普通工作文件中选择行后暂存。文件尚未保存时，Ash 会询问是否先保存。部分暂存不支持冲突、重命名、子模块、二进制和非 UTF-8 文件。

如果提示比较内容已变化，从 Git 侧栏重新打开当前比较，再选择内容。不要继续使用旧比较的行号。

## 创建提交

1. 检查 **Staged Changes**，确认已暂存的文件和修改范围。
2. 在 **提交信息** 中填写本次修改的说明。
3. 选择 **Commit** 按钮，或在输入框中按 Windows、Linux 的 `Ctrl+Enter`，macOS 的 `Command+Enter`。
4. 查看提交成功提示，并检查剩余更改。

主提交按钮只提交暂存区。未暂存的更改会继续留在工作文件中。提交成功后，如果你没有在提交过程中继续编辑说明，输入框会清空。

需要一次提交全部更改时，在命令面板运行 **Git: 提交全部更改**。Ash 会让你选择仅包含已跟踪更改，还是同时包含未跟踪更改。选择包含未跟踪更改时，忽略规则仍然生效。提交前仔细检查范围，避免把临时文件一起加入。

名称中带 **签署说明**（Sign-off）的提交命令添加 `Signed-off-by` 尾注。它使用已有 Git 身份，不会替你配置姓名、邮箱或 GPG 签名。

提交写入本地历史。要把提交发送到远端，还需要推送。

## 创建和切换分支

1. 在命令面板运行 **Git: 创建分支**，输入新名称。新分支从当前提交创建，当前分支保持不变。
2. 选择底部状态栏的分支名称，或运行 **Git: 切换分支**。
3. 选择要使用的本地分支，完成后再次核对状态栏。

切换失败时，先检查尚未提交的修改，以及目标分支是否正在其他工作树中使用。不要为了强行切换而直接丢弃不确定是否需要的更改。

清理分支时，运行 **Git: 删除分支**，选择其他本地分支并确认。Ash 不会通过这个操作强制删除未合并分支，也不会删除正在任何工作树中检出的分支。

## 获取、拉取和推送远端更新

远端操作使用当前仓库的 Git 配置。先确认当前分支、远端和认证信息正确。

* 获取远端引用：运行 **Git: Fetch**。有多个远端时，选择要获取的远端。命令 **Git: Fetch From All Remotes** 获取所有已配置远端的更新。
* 拉取到当前分支：打开 **更改** 视图的 **更多操作 > 拉取、推送 > 拉取**。普通拉取遵循 Git 的 `branch.<分支名>.rebase`、`pull.rebase` 和 `pull.ff` 配置；选择 **拉取（变基）** 则明确使用变基。
* 推送当前分支：完成提交后，在同一菜单选择 **推送**，把本地提交发送到已配置的远端。

**图表** 标题栏也提供获取、拉取和推送操作。获取只更新远端引用，不会把远端修改合入当前工作文件。拉取可能合并或变基本地历史，具体取决于仓库策略。分叉且没有配置整合策略时，Git 会拒绝继续，Ash 不会替你选择默认策略。

### 同步当前分支

选择 **同步更改** 或底部状态栏的同步图标，会执行当前分支的远端同步。

1. 核对确认框中的上游远端分支。默认启用 `git.confirmSync`，选择 **取消** 会在获取、拉取和推送前停止；选择 **确定，不再显示** 会关闭以后同步时的确认提示。
2. 确认后，Ash 从刚核对的上游拉取。同步默认遵循 Git 配置；开启 **同步时变基**（`git.rebaseWhenSync`）或选择 **同步更改（变基）** 会使用变基。
3. 拉取完成后，只有仍有待推送提交时才推送。发生冲突、取消操作或分支目标变化时，不继续推送。

配置为只读的远端（`no_push`）只拉取，不显示双向同步确认，也不推送。状态栏只显示传入计数。

### 发布尚未跟踪的分支

当前分支没有上游时，同步入口会转到 **发布分支**。先创建至少一个提交，并配置可写远端，再选择要发布到的远端。多个远端时，选择器还提供 **添加远端** 入口。

发布把本地分支推送到选定远端并建立跟踪关系。它不创建新的 GitHub 仓库；需要创建托管仓库时，使用下一节的独立入口。

### 发布到新的 GitHub 仓库

在 Ash 中登录有创建仓库权限的 GitHub 账号后，运行命令面板中的 **GitHub: Publish Repository**（`github.publish`）。

1. 选择本地仓库。尚未初始化或没有首次提交时，按提示完成初始化、检查文件并创建提交。
2. 确认 GitHub 账号，输入仓库名称，选择私有或公开。默认选项是私有仓库。
3. 已有 `origin` 时，输入新的远端名。
4. 在最终确认中核对账号、可见性和分支，并检查已提交历史中没有密钥或其他不应公开的内容。
5. 发布后打开返回的仓库地址，确认分支和文件。

发布只推送该分支的已提交历史，未提交文件不会上传。如果仓库创建结果不确定，先去 GitHub 检查；如果仓库已创建但推送失败，保留该地址，检查远端配置后重试 **发布分支**，不要再次创建仓库。

### 查看进度与认证问题

同步、拉取、推送和发布执行期间，状态栏同步图标会旋转。`git.showProgress` 控制操作进度显示；启用 `git.supportCancellation` 后，获取和拉取可以取消，关闭进度显示不影响这个取消能力。推送没有取消操作。

GitHub HTTPS 操作可以使用 Ash 已登录的 GitHub 凭据，由 `github.gitAuthentication` 控制。其他远端或 SSH 操作仍需相应 Git 认证。认证失败时，检查当前远端使用的协议和对应账号权限，不要把能够浏览 GitHub 仓库视为已经具备 Git 推送权限。

## 浏览历史和撤销操作

展开 Git 侧栏中的 **图表**，查看提交与分支关系。向后浏览时会继续加载历史。展开提交可以查看文件列表，再选择文本文件查看该次提交的更改。

### 查看单个文件的时间线

1. 在编辑器中打开要检查的仓库文件。
2. 在命令面板运行 **聚焦时间线视图**，查看该文件的 **时间线**。如果没有显示 Git 提交，在视图操作中确认已选中 **Git 历史记录** 来源。
3. 选择一条 Git 提交，打开该次提交与其父提交的只读比较。文件重命名前的历史使用当时的路径，不会把旧内容写回当前文件。
4. 向下滚动到底部，自动加载更早的记录。追加加载失败时，选择 **重试加载**。需要重新读取历史时，使用视图的 **刷新** 操作。

时间线默认跟随当前文件。需要切换编辑器但保留同一文件的历史时，在视图操作中启用 **固定当前文件**。同一视图中的 **本地历史** 条目比较保存的版本与当前文件，不代表 Git 提交。

`timeline.pageSize` 控制每页条目数，不限制可浏览的历史总数。Git 时间线默认显示作者和提交日期；`git.timeline.showAuthor` 和 `git.timeline.date` 可以调整显示。开启 `git.timeline.showUncommitted` 后，时间线还会显示该文件已有的暂存和工作树更改条目。

也可以在打开文件后运行 **Git: 文件时间线**，从列表中选择提交。这个入口通过 **加载更多** 继续浏览较早历史，而不是自动滚动加载。

### 查看当前行归属

在仓库文件中移动光标，状态栏右侧、光标位置旁会显示当前行的 Git 作者和时间。悬停可查看提交说明和提交标识。`git.blame.statusBarItem.enabled` 控制这项显示，默认开启；需要在代码行旁显示归属时，开启 `git.blame.editorDecoration.enabled`。

### 选择合适的撤销操作

撤销前先分清要改变的内容：

* 只调整下一次提交的范围：取消暂存，工作文件保留。
* 只还原工作文件中的某个更改块或选中范围：从可编辑的单文件比较使用 **还原更改** 或 **还原选中的更改**，检查结果后保存。这些编辑可以撤销，不修改暂存区。
* 丢弃工作文件中的更改：使用文件旁的放弃操作并确认。此操作会丢失选中的未提交修改，不删除未跟踪文件。
* 修改最后一次提交：运行 **Git: 修改最后一次提交**。说明为空时会加载上次提交说明，再让你确认改写历史。
* 撤销最后一次提交：运行 **Git: 撤销最后一次提交**并确认。该操作保留暂存区和工作文件，不支持撤销仓库的根提交。

修改或撤销最后一次提交会改写历史。对已经共享的提交，先与协作者确认处理方式。

## 排查常见问题

### 没有看到仓库或更改

确认打开的是正确项目文件夹，Git 为 2.40.0 或更新版本，文件已经保存。升级 Git 后重启 Ash，再运行 **Git: 刷新**。未被 Git 跟踪的文件也可能因忽略规则而不在列表中。

### 提交按钮不可用或提交失败

确认已经暂存文件、填写提交说明，并处理合并冲突。检查仓库的 Git 身份配置和目录访问权限。失败后提交说明会保留；如果刚使用提交全部更改，部分内容可能已经进入暂存区，重试前重新检查 **Staged Changes**。

### 拉取失败

先获取更新并检查 **图表**。本地与远端分叉时，确认仓库已按项目约定配置合并或变基策略；`pull.ff=only` 会拒绝非快进拉取。发生整合冲突时，从 **Merge Changes** 处理文件，再继续或中止对应操作。同步在冲突解决前不会继续推送。

遇到上游历史改写或标签冲突提示时，先核对远端变化，再决定是否继续或替换标签。取消后检查当前仓库状态，不要反复选择拉取来替代处理问题。

### 需要查看具体错误

运行 **Git: 显示 Git 输出**，结合通知中的错误检查身份、远端、认证或权限。需要处理合并冲突时，从 **Merge Changes** 打开冲突文件，完成并保存结果后继续对应的 Git 操作。
